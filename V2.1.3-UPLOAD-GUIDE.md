## 🎓 Understanding the Pattern

### Why Git LFS?
```
Regular Git: Stores full history of every file version
Problem: 136MB × multiple versions = repo bloat

Git LFS: Stores pointer in repo, binary in separate storage
Solution: Repo stays small, LFS handles large files efficiently
```

### Why One File at a Time?
1. **Reliability**: Large uploads can timeout; one file = easier retry
2. **Tracking**: Each file gets its own commit with metadata
3. **Visibility**: Clear progress and history
4. **Rollback**: Easy to revert individual files if needed

## 🎓 Key Concepts

### Git LFS Flow
```
Local:
  file.AppImage (136 MB actual file)
  ↓
  git add
  ↓
  .git/lfs/objects/... (LFS stores locally)
  
Remote (GitLab):
  repo: pointer file (tiny, ~100 bytes)
  LFS storage: actual binary (136 MB)
```

### Why .gitattributes Matters
```
release/**/*.AppImage filter=lfs diff=lfs merge=lfs -text
```
This tells Git: "Any .AppImage in release/ directories = LFS, not regular Git"

### Benefits
- ✅ Repo size stays small (~50 MB)
- ✅ Clone times stay fast (LFS downloads on demand)
- ✅ Full version history without bloat
- ✅ Binary files handled properly

### Best Practices
1. **One commit per file**: Clear history
2. **Rich metadata**: Size, checksums, platform
3. **No-verify flag**: Skip pre-commit hooks (already tested)
4. **Descriptive messages**: Future you will thank you
